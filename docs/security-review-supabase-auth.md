# Security Review: Supabase Auth & RLS Migration

This document assesses the ACIS architecture against key **OWASP Top 10** categories following the migration from Telegram OTP/session cookies to Supabase Auth (Google OAuth) and PostgreSQL Row-Level Security (RLS).

---

## 1. OWASP A01: Broken Access Control

### Assessment: **SECURE & VERIFIED**
- **Row-Level Security (RLS) Policies:** Enabled on all core tables (`users`, `families`, `family_members`, `wallets`, `transactions`, `proposals`, `pending_notifications`).
- **Fail-Closed Dual Pool Database:**
  - Application requests execute via `userPool` using the restricted role `acis_app` (`NOBYPASSRLS`).
  - Every user query is bound in a transaction executing `SET LOCAL ROLE authenticated` and `set_config('request.jwt.claims', ..., true)`.
  - Database queries automatically evaluate `auth.uid()` and `public.is_family_member(family_id)` security definer function.
- **Repository-Level Filters:** All domain repositories enforce explicit `family_id` and `user_id` query constraints in addition to database-level RLS, providing defense-in-depth against unauthorized access.
- **Internal Endpoints Isolation:** `/api/v1/internal/*` and `/api/v1/bot/*` require `X-Bot-Secret` validation via `BotSecretMiddleware`.

---

## 2. OWASP A02: Cryptographic Failures & Secret Management

### Assessment: **SECURE & VERIFIED**
- **Zero Secrets in Repository:** No database credentials, service role keys, bot tokens, or private signing keys are committed in code.
- **Manual App Role Password:** `acis_app` login password is created directly in Postgres / Supabase and supplied via runtime environment variables (`DATABASE_APP_DSN`).
- **Asymmetric Signature Verification:** JWT authentication uses ES256 (ECC P-256) asymmetric keys fetched directly from Supabase's public JWKS endpoint (`/auth/v1/.well-known/jwks.json`).
- **Frontend Token Exposure Safety:** Frontend only holds `VITE_SUPABASE_ANON_KEY` (safe for browser exposure). The `service_role` key is strictly restricted to backend administrative tasks and never exposed to the frontend.

---

## 3. OWASP A03: Injection & Parameterized Configuration

### Assessment: **SECURE & VERIFIED**
- **Parameterized SQL:** All queries in `apps/backend` use parameterized prepared statements via `sqlx` and PostgreSQL placeholders (`$1`, `$2`).
- **Safe RLS Context Injection:** Context claims injection executes `SELECT set_config('request.jwt.claims', $1, true)` with JSON claims passed exclusively via query parameter binding, eliminating SQL injection risk in session configuration.

---

## 4. OWASP A05: Security Misconfiguration

### Assessment: **SECURE & VERIFIED**
- **Strict Environment Configuration:** Backend configuration is loaded hierarchically from `acis-config.yaml` with explicit environment variable overrides (`DATABASE_APP_DSN`, `DATABASE_ADMIN_DSN`, `SUPABASE_JWKS_URL`, `BOT_INTERNAL_SECRET`, `REDIS_URL`).
- **Transaction-Local Claims:** `set_config(..., is_local = true)` ensures claims are local to the active transaction and cannot leak across pooled database connections.
- **CORS & Headers:** CORS policies restrict allowed origins and exposed headers.

---

## 5. OWASP A07: Identification and Authentication Failures

### Assessment: **SECURE & VERIFIED**
- **Supabase-Managed Identity Provider:** Google OAuth authentication is delegated to Supabase Auth, removing legacy custom OTP generation, AES-GCM encryption in Redis, and home-rolled session cookie rotation.
- **Strict JWT Validation:** Token claims validation enforces `sub` (UUID), `aud: authenticated`, and `exp` timestamp. Expired or altered tokens are rejected with HTTP 401.
- **Secure Account Linking:** Bot account linking requires a time-limited (10 minutes) 6-character one-time code generated by an authenticated session (`/api/v1/telegram/link-code`) and verified server-side.
